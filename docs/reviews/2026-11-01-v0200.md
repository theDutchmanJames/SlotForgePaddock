# Review of v0.20.0 changes — 1 November 2026

Scope: the changes after the previous review, released in commit `9eb6832`
(v0.20.0), compared with `525b8ab` (v0.19.1). Inspection covered the shared
Dealership password, legacy-host separation, connection persistence, Timing
permissions, JSON encoding and photo caches, desktop snapshot patches, refresh
ordering, tests, release notes and the Timing handoff. The fixes below are included in v1.0.0; they were not included in the
published v0.20.0 assets.

## Findings fixed

| Area | Finding | Correction |
| --- | --- | --- |
| Replication verification | Deep equality ignored object key order, while replication hashes cover exact JSON bytes. A corrected Timing payload with reordered fields could reconstruct equivalent values but fail its digest, marking a connected copy outdated. | Delta comparisons now preserve field order, including nested objects and record roots. The fix uses existing patch operations, so the replication wire format is unchanged. |
| First connection durability | Pairing and its password were saved before the downloaded copy reached disk. A failed copy write, combined with a leftover copy from another dealership, could strand subsequent connection attempts. | Persist the verified copy before its pairing. Check the complete saved-copy identity before deciding a download can be skipped. Failed writes do not remember a new pairing. |
| Reconnect failure | Reconnecting closed the working update stream before saving connection settings. A settings-write failure unnecessarily disconnected an otherwise working copy. | Commit the settings before replacing the existing connection. A failed save retains the stream, credential and saved pairing. |
| Initial hosting failure | Dealership setup could save successfully but fail to start its listener, leaving the setup form open and subsequent attempts reporting that the collection was already shared. | Reload the saved state, explain the hosting failure and expose Start Dealership as the retry action. The chosen password stays saved. |
| JSON writer memory | Saving a catalogue retained every generated token object and then allocated another array for its strings. Large collections needed substantially more temporary memory than their JSON size. | Join tokens in bounded batches. A synthetic 50,000-record, 20-field workload produced identical 25,877,813-byte JSON; peak process memory fell from approximately 801 MiB to 330 MiB in separate local runs. |

Also removed the obsolete Dealership option from the legacy password-dialog
lookup. Corrected a privacy test that used the now-inactive browse credential:
it now requires a successful authorised public-catalogue response before checking
that private data is absent, instead of accidentally checking an error response.

## Validation

- **342 automated tests passed**, with zero failures or skipped tests.
- **189 isolated Electron workflow checks passed**, with no captured renderer
  errors. Includes recovering from a deliberately failed first hosting start.
- Password changes were checked against existing push streams and an already
  started Timing upload; revoked credentials cannot finish saving that upload.
- A real local host/copy test applied a reordered Timing correction and verified
  the reconstructed collection hash, without marking the copy outdated.
- **2,000 deterministic plain-JSON round trips** checked mixed nested records,
  changes, exact reconstructed JSON, hashes and encoder output.
- The released delta code reproduced the key-order failure; the corrected code
  passed the same case. Large-string escaping, Unicode, byte counts, snapshots,
  photo validation, retries, rollback and baseline isolation remain covered.
- Application syntax checks and `git diff --check` passed.
- The existing 27 MiB photo benchmark completed: workshop save 116 ms,
  proposal 216 ms, review preview 36 ms and approval 159 ms in this run.
  This was run alongside desktop testing and is not a controlled comparison.

## Limits and compatibility

Tests use disposable databases and an isolated application profile. Network
checks use local HTTP on one Windows computer, not a new physical Wi-Fi test.
The memory figures are single-run process peaks for synthetic data, not a memory
cap or a promise of pause-free saves. Initial photo transfers and durable disk
writes still incur work.

No database schema, Timing v1 contract or credential requirements changed in
this review. No Timing source or user collection was modified. The review itself did not
publish a release; packaging and publication followed separately for v1.0.0.
